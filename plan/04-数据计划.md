### 1.2 不入仓的原料

| 原料 | 处置 | 理由 |
|---|---|---|
| 头文件 `.h` 原文 | `_headers/`，`.gitignore` 封 | 入库的是**抽取结果**，不是原料；原文体积大且可随时用 `gh api` 重取 |
| `nodejs.org/api/errors.html` | `_headers/` | 415 KB HTML，抽取后只剩常量表 |
| 本机 `os.constants.errno` 的原始 dump | `tmp/` | 只有抽取后的 YAML 入仓；`verified_at` 记录核验日期 |

**纪律**：任何一条入仓数值背后都必须有一份"能重跑出它"的取数命令。
落到两个脚本上（都是 dev 侧，**都不参与构建** —— 构建只读入仓 YAML，见 `plan/02` D2）：

| 脚本 | 做什么 | 产出 | 自检 |
|---|---|---|---|
| `tools/fetch_sources.py` | 走 `gh api repos/<o>/<r>/contents/<path>` 取 5 份原文；记 commit sha + sha256 | `_headers/*.h` + `_headers/SOURCES.json` | `--check` 对 sha256（防本地原料被手改） |
| `tools/extract_catalog.py` | 按用户态默认编译环境求值 `#if` 链，逐条抽 `#define`；两个运行时视角实读 | `data/catalog/*.yaml`（599 条） | `--check` 与仓库 YAML 逐字节比对；`--report` 打印被排除项 |

> **为什么拆成两个脚本而不是一个**：取数要联网（`gh`），抽取要**零网络**。
> 合成一个会让"只想验数据对不对"的人也被迫联网 —— 而 `--check` 恰恰要在离线环境里能跑。
>
> **行号由解析器给出，不由人手填**。手填的行号与原文对不上时 `source` 就退化成安慰剂，
> 而 `source` 是"每条数值带出处"的唯一凭据。这条由
> `tests/test_catalog_data_m1.py::test_every_file_entry_line_points_at_its_own_define` 守住
> —— 它按行号回原文取那一行，断言 `#define` 的名字就是条目名（改错一位立刻红）。

> **"逐条"的技术含义**：头文件里的 `#define` 并非都在同一编译环境下可见，所以抽取器要
> 按写死的默认环境（macOS `__DARWIN_C_LEVEL=FULL` / `__DARWIN_UNIX03=1`；Linux 用户态）
> 求值 `#if` 链，**只收可见分支**，不可见分支逐条写进 `data/gaps.md` 并给出原因。
> 不做这一步就会出现两种假象：把内核内部伪错误当用户态 errno，或把 `EOPNOTSUPP` 抄成
> 45（非 UNIX03 分支）而实际用户态是 102。

## 2. 真值纪律

### 2.1 每条数值带出处（fail-closed）

| 阶段 | 判据 | 失败行为 |
|---|---|---|
| YAML 装载 | `name` / `domain` / `value` / `source` 齐备 | `CatalogError`，退出 3 |
| `source.kind` | ∈ `{file, runtime, doc}`，且各 kind 的必填字段齐 | 同上 |
| `kind: file` | `file` 非绝对路径 + `line` 为正整数 + `repo` 非空 | 同上 |
| `kind: runtime` | `runtime` ∈ `{node, python}` + `program_version` + `verified_at` ISO 日期 | 同上 |
| `kind: doc` | `url` 是 https + `anchor` 非空 | 同上 |

**无出处者不得入编目** → 记 `data/gaps.md`，一行一条：`| 常量 | 平台 | 域 | 为什么没入 | 补的路径 |`

### 2.2 判定强度三值封闭（外部数值一律三态化）

编目里的每个 `value` 本身就是一个"外部数值"，按三态处理：

| 字段 | 取值 | 含义 |
|---|---|---|
| `verified` | `true` / `false` | 是否已核对原文（`data/README.md` §1 的 ✅/⬜ 逐条对应） |
| `basis` | `header` / `runtime` / `doc` / `convention` | 这个值的**依据类型** |
| `verified_at` | ISO 日期 / `null` | 核验日期 |

**硬纪律（三值封闭，不可升级）**：

| 强度 | 可用于什么 | 本项目的对应 |
|---|---|---|
| `hard` | 能指到"文件 + 行号"的逐字原文 | `kind: file` 的条目 |
| `diff` | 能指到"运行时实读"或"官方文档锚点"，但**不能指到行号** | `kind: runtime` / `kind: doc` |
| `gray` | 只有惯例，没有原文 | `128+n` 规则、`sysexits` 的"约定非标准"标注 |

> **`gray` 的条目一律不许用确定语气**：报告里必须出现 `"惯例非标准"` / `"约定非标准"` 字样。
> 这条由 `explain` 的 `notes` 字段承载，`bench` 断言该字样存在——**不是靠人记得写**。

### 2.3 `sysexits` 与 `128+n` 的强度差异（为什么不能放同一格）

| 项 | 强度 | 理由 |
|---|---|---|
| `sysexits` 64–78 的**码值与名字** | `diff` | `man.openbsd.org` 是官方文档页，可锚到段落，但**不是标准正文** |
| `sysexits` 的"是否标准" | `gray` | 它明确是 **convention**，报告必须标注 |
| `128+n` | `gray` | shell 实现惯例；POSIX 正文没有这条。**报告必须写"惯例"** |

### 2.4 真值只存输入与期望

`fixtures/<case>/expected.json` 存**结果对象**（`verdict` / `attribution` / 退出码 / `sources` 命中集合），
**不存渲染文本**——渲染是呈现层的事（`plan/02` D4）。

## 3. 生成与校验

| 命令 | 输入 | 输出 | 确定性判据 |
|---|---|---|---|
| `tools/build_catalog.py --out <dir>` | `data/catalog/*.yaml` | `catalog.json` + `catalog.manifest.json` | 双跑逐字节一致 |
| `tools/build_catalog.py --check` | 同上 | 与仓库冻结件比对 | 逐字节；不一致 exit 1 |
| `errcode-atlas build --check` | 随包 `catalog.json` + manifest | 摘要校验 + 结构校验 | 摘要不符 → exit 3 |

**为什么两道 check**：第一道验"生成器与仓库件一致"（dev 侧），第二道验"装好的包里的件没坏"（用户侧）。
只有前者时，`pip install` 之后没人知道随包数据还对不对。

### 3.1 摘要口径（关键，踩过的那种坑）

`catalog.json` 的 sha256 **按行尾归一后计算**：`text.replace("\r\n", "\n")` 再 `sha256`。
配套 `.gitattributes` 写 `* text=auto eol=lf`。

> 不这么做的话：`git archive` 导出的树受 `core.autocrlf` 影响变成 CRLF → 从导出树构建的包装好即 exit 3，
> 而开发机上永远绿。这是"内容寻址的随包数据"那条纪律的直接落法。
