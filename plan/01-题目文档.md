## 一、介绍：同一个名字，三个数字

同一台机器、同一时刻（2026-11-01，win32 x64），两个运行时对**同一个错误名**给出两个数值：

```
$ node -e "console.log(require('os').constants.errno.EADDRINUSE)"
100

$ python -c "import errno; print(errno.EADDRINUSE)"
10048
```

再看三个平台对**同一个常量名**的定义（全部读自公开头文件，见 `data/README.md` §1）：

| 常量 | Linux | macOS | Windows（Node/VC） |
|---|---:|---:|---:|
| `EAGAIN` | **11** | **35** | 11 |
| `EADDRINUSE` | **98** | **48** | **100** |
| `ECONNREFUSED` | **111** | **61** | **107** |
| `ETIMEDOUT` | **110** | **60** | **138** |
| `ENOTEMPTY` | **39** | **66** | 41 |
| `ELOOP` | **40** | **62** | 114 |

**同一列的四个数字，没有一个能跨平台通用。** 而 AI 的默认行为是"记住一个"然后到处用。

信号编号同样分裂——**从第 7 号就开始分叉**：

| 信号 | Linux | macOS |
|---|---:|---:|
| `SIGBUS` | 7 | **10** |
| `SIGSTKFLT` | 16 | （无此信号） |
| `SIGSTOP` | 19 | **17** |
| `SIGCHLD` | 17 | **20** |
| `SIGUSR1` | **10** | **30** |

于是 **`exit 137` 的解读也必须先问平台**：POSIX 惯例是 `128 + n`（n 为杀死进程的信号），
`128 + 9 = 137` → `SIGKILL`。但**这只是惯例，不是标准**，且 Windows 上 `18446744072635809792`
一类巨大退出码的语义完全不同。

本项目的判定对象只有一句话：

> **给定「一个数字 + 一个平台 + 一个语境」，它能不能被唯一归因；
> 能，归到哪一条；不能，为什么要说"不能"。**

不是"错误码字典全文检索"（那是文档 MCP 的领域，`context7` 64033★ 已占），
不是"帮我修这个 bug"（见 §六 非目标），
不是"给这条错误码写一段解释文字"（那是模型擅长且容易编造的事，正是本案要取代的）。

## 二、任务要求（模块化）

> **首期范围**：四个模块，锁死 **Linux / macOS / Windows 三平台** × **POSIX errno + 信号 + 进程退出码** 三个域。
> **不承诺** SQLite 结果码、HTTP 状态码、各数据库驱动的私有错误码（见 §六）。

### 模块 ① 编目构建（`build`）

- **输入**：随包登记的三平台头文件摘录（`data/catalog/` 下的结构化 YAML，**含出处行号**）；
- **输出**：统一编目 `catalog.json`——每条形如
  `{name, linux: {value, source}, macos: {value, source}, windows: {name, value, source}, description, posix_ref}`；
- **引擎**：YAML → JSON 的确定性变换，**零模型**；
- **确定性纪律**：每条数值**必须带出处**（文件 + 行号或 URL 锚点）；无出处者**不得入编目**，
  记入 `data/gaps.md`；
- **⚠️ 硬纪律**：**只允许收录已核对原文的常量**。未核对的一律 `⬜` 且不参与判定
  （踩 preflight ① 与「引用纪律」）。

### 模块 ② 数字→语义判定（`explain`）—— 本题招牌

- **输入**：`<number>` + `--platform linux|macos|win32` + `--domain errno|signal|exit`;
- **输出**：判定结果，五态：
  | 判定态 | 含义 |
  |---|---|
  | `UNAMBIGUOUS` | 该数字在该平台该域下唯一对应一个常量 |
  | `AMBIGUOUS-SAME-PLATFORM` | **同平台同域内一数多名**（如 Linux `SIGABRT` 与 `SIGIOT` 同为 6） |
  | `AMBIGUOUS-CROSS-PLATFORM` | 给了数字但未给平台，且各平台不一致 |
  | `PLATFORM-ABSENT` | 该常量在该平台**不存在**（如 macOS 无 `SIGSTKFLT`） |
  | `UNKNOWN` | 编目内无此值（可能为私有/自定义错误码） |
- **确定性纪律**：`AMBIGUOUS-*` **不是失败态**，是**正确的判定结果**；
  报告必须列出全部候选并给出区分方式，**不得任选一个冒充唯一答案**。

### 模块 ③ 退出码归因（`exitcode`）

- **输入**：进程退出码 + 平台；
- **输出**：归因判定：
  - `SIGNAL-KILLED(n)` ——当退出码落在 `128 + n` 且 `n` 在该平台确实是有效信号时；
  - `NORMAL-EXIT` ——0–127 且非约定保留段；
  - `SYSEXITS(n)` ——命中 `sysexits.h` 的约定值（64–78），**必须标注"约定而非标准"**；
  - `UNATTRIBUTABLE` ——**不可唯一归因**（如 `exit 1` 是通用失败、无特定语义）；
- **确定性纪律**：**`exit 1` 必须判 `UNATTRIBUTABLE`**，不得强行解释成任何具体错误；
  `128+n` 规则**必须同时检查 `n` 是否为该平台有效信号**，否则一律 `UNATTRIBUTABLE`。

### 模块 ④ 报告与退出码（`report`）

- **输出**：人读表 + `--json` 机读；
- **退出码语义**（唯一定义见 `data/README.md` §5）；
- **确定性纪律**：`UNKNOWN`（编目无此值）与 `UNAMBIGUOUS`（命中）**必须退出码可区分**。

## 六、边界与非目标

**不做清单**：

- ❌ **不做全文检索/文档问答**（`context7` 64033★ 领域，本案只做**编号→语义判定**）；
- ❌ 不解释具体 bug 成因（"为什么我的连接被拒"）——只回答"这个码是什么意思"；
- ❌ 首期**不做** SQLite 结果码 / HTTP 状态码 / 数据库驱动私有码 / gRPC 状态码；
- ❌ 不联网查 registry 或文档站（编目随包分发）；
- ❌ 不承诺"覆盖全部错误码"——编目覆盖度以 `data/README.md` §4 口径为准，**未覆盖即 `UNKNOWN`**。

**⚠️ 必须写死的免责**：

> 本工具给出的是**公开头文件与官方文档的编目结果**，不是对任何具体崩溃的成因判断。
> `UNATTRIBUTABLE` / `AMBIGUOUS` 是**正确且常见**的结论，**不代表工具失效**。
> `128+n` 是**POSIX 惯例而非标准**，`sysexits` 是**约定而非标准**——两者在报告中都必须如此标注。

**隐私红线**：纯本地，零上传；编目只含公开常量；报告不含用户路径与进程信息。

**品牌隔离**：与系列 `10-27-versionaudit`（版本约束审计）、`11-1-depcheck-live`（依赖调用面对账）
**文档互不提及**。切割点：versionaudit 判 semver 约束是否成立；depcheck-live 判导出面是否认得调用；
本案判**数字→语义的唯一性**。

**结论纪律**：每条判定必须附**出处锚点**（头文件路径 + 行号，或官方文档 URL 锚点）；
无出处不得给确定语气；跨平台差异**必须逐平台列值**，不得只给一个。
