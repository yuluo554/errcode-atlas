## 一、这个工具要解决的问题

AI 在任何一次 debug 里都会遇到 `EACCES`、`ECONNREFUSED`、`exit 137`、`errno 28`。
它对这类问题的回答通常来自三处：被污染的博客摘要、按名字记住的旧值、或者直接猜。

**问题不在于它答得少，而在于它答得太像。** 一句"`exit 137` 是 SIGKILL"在 Linux 上是对的，
在 `win32-python` 上就是编的；一句"`EAGAIN` 是 11"在 Linux 上是对的，在 macOS 上 11 是 `EDEADLK`。
错答与对答长得一模一样 —— 这才是要治的病。

所以本项目的判定对象只有一句话：

> **给定「一个数字 + 一个平台 + 一个语境」，它能不能被唯一归因；能，归到哪一条；不能，为什么要说"不能"。**

这句话决定了整份设计：**"不能"必须是可表达、可机读、且不是失败的结论**。

## 二、三个设计决定，以及它们各自挡住了什么

### 2.1 判定结果有五个态，而不是"对/错"

两态模型（答得出 / 答不出）会把三种完全不同的事实压成一句"答不出"：

| 事实 | 为什么不能合并 |
|---|---|
| 同平台一数多名 | **答案不止一个，但都是真的**。合并进"答不出"会让工具显得比实际更无能 |
| 跨平台不一致 | **问题是缺了一维信息**（平台）。合并进"答不出"会让用户以为编目没覆盖 |
| 编目里根本没有 | **这才是真的没有**。与前两者混同，用户会去"补编目"补一个不存在的条目 |

五个态各自的判据见 `data/README.md` §5.2。这里要说的是**为什么封闭在五个**：

- 加第六个态表达"Windows 双视角"会把**平台轴的属性**写成**判定结果的性质**。
  `win32-node` 与 `win32-python` 是两个平台值，不是一个判定态（`plan/02` D3）。
- 态数不封闭，`bench` 的唯一值集断言就没有分母，语料可以无限膨胀而"覆盖度"无从定义。

**真跑证据**（`errcode-atlas explain 11`，未给平台）：

```console
$ py -3.12 -m errcode_atlas explain 11
# 判定：AMBIGUOUS-CROSS-PLATFORM

- 语义：未给平台且各平台归因不一致（正确结果，非失败）
- 查询：11 · 平台未指定 · 域自动探测

## 逐平台
| 平台 | 归因 |
|---|---|
| linux | EAGAIN, EWOULDBLOCK, SIGSEGV |
| macos | EDEADLK, SIGSEGV |
| win32-node | EAGAIN, SIGSEGV |
| win32-python | EAGAIN, SIGSEGV |

## 如何区分

未指定平台，且各平台对该数字的归因不一致；逐平台列值，必须用 --platform 指定后才有唯一答案
```

注意这条输出里的两件事：**数字 `11` 同时是 errno 与信号编号**（所以 linux 一行有三个名字），
以及 **`11` 在 macOS 上是 `EDEADLK` 而不是 `EAGAIN`**。这正是"记住一个数字到处用"会踩的坑。

### 2.2 歧义的定义是"一个问题两个答案"，不是"两个平台给不同的数"

这是全项目最容易搞反的一条。`EAGAIN` 在 Linux 是 11、macOS 是 35、Windows 是 11 —— 数值确实不同，
但问 `EAGAIN` 问的是"**这个名字有没有定义**"，四个平台都有，**答案唯一**，所以它判 `UNAMBIGUOUS`。

判据是：**这个查询问的是"数字是什么"，还是"名字在不在"？** 只有前者会因跨平台失去唯一性。

这一条是在 M2 实测中发现的：M1 时 `explain EAGAIN`（无平台）返回 `UNAMBIGUOUS` 并列 11/35/11/11，
而判定态判据表把 `EAGAIN → 11/35/11` 举作跨平台歧义的**样本** —— 两处口径直接冲突。
M2 的板拍在"名字查询确有唯一答案"这一侧，并把判据表的举例改成**数字查询**（`plan/06` G6）。

> **教训**：文档里举例时挑错样本，比写错规则更难发现 —— 规则读起来对，例子是反的。
> 抓它靠的是"实现跑出来的结果与文档举例对不上"，也就是必须有真跑。

### 2.3 每条数值必须带出处，且强度不可升级

编目里每条都带 `source` 块，三态 fail-closed：`file`（文件 + 行号）、`runtime`（程序 + 版本 + 实读日期）、
`doc`（URL + 页内锚 + 核对日期）。装载期缺一个字段就抛错，不做"跳过一条继续"。

**强度不可升级**：`runtime` 与 `doc` 永远拿不到 `hard`（`plan/04` §2.2）。原因很实际 ——
只有 `file` 能指到"第几行第几个字符"，`runtime` 只能指到"某版本某程序读过一次"，
`doc` 只能指到"某页某锚"。把它们标成同一档，报告里的"出处"就成了装饰。

最硬的一条是 `128+n`：**POSIX 标准里没有这个公式**。M1 核对了 POSIX.1-2017 的 `wait()` 页 ——
`WEXITSTATUS` 只取低 8 位，信号终止走 `WTERMSIG`，全文无 `128+n`。
所以它是 **shell 实现惯例**，报告中必须写"惯例非标准"。

强制措辞由三层兜住，不靠人记得写：

1. `gray` 强度（`plan/04` §2.3）；
2. `notes` 里必须出现"惯例非标准"/"约定非标准"字样；
3. `selftest._check_gray_markers` 与 `tests/test_exitcode.py`、`bench` 的 `require_note_markers` 断言它存在。

**真跑证据**（`errcode-atlas exitcode 137 --platform linux`）：

```console
$ py -3.12 -m errcode_atlas exitcode 137 --platform linux
# 归因：SIGNAL-KILLED

- 语义：按 128+n 归因到信号（POSIX 惯例）
- 退出码：137 · 平台 linux
- 信号：9（SIGKILL）

## 说明

- 128+n 归因是 POSIX 惯例非标准（即惯例而非标准）
- n=9 已核对：在 linux 上是有效信号（SIGKILL）

## 出处

- include/uapi/asm-generic/signal.h:20
```

`n=9 已核对：在 linux 上是有效信号` 这一行是 `128+n` 的第二半纪律：**必须验证 `n` 在该平台确实是有效信号**。
Linux `SIGKILL`=9 → `137` 成立；但若平台无 `n` 号信号，`128+n` **不成立**，须判 `UNATTRIBUTABLE`
（语料 `fixtures/e-exit-137-win32-python-invalid-n` 就是这条的反例）。

## 三、编目为什么长这样

### 3.1 Windows 必须是两个平台值

同一台机器、同一时刻，两个运行时对同一个错误名给出两个数值：

```console
$ node -e "console.log(require('os').constants.errno.EADDRINUSE)"
100

$ py -c "import errno; print(errno.EADDRINUSE)"
10048
```

只写一个 `windows` 值是**从第一行就错**的编目。所以平台轴上有 `win32-node` 与 `win32-python`，
且 `--platform win32` / `--platform windows` 会被**显式拒绝**（退出码 `4`）并提示两个视角 ——
静默映射到其中一个比报错更危险：用户会拿到一个他从未要求过的答案。

> 顺带一个真实的歧义来源：Python 视角下 `10048` 同时是 `EADDRINUSE` 与 `WSAEADDRINUSE`，
> 于是同一台机器上 `AMBIGUOUS-SAME-PLATFORM` 是**真实存在**的，不是编造出来的用例。

### 3.2 平台值的数值没有一个能跨平台通用

`EAGAIN` / `EADDRINUSE` / `ECONNREFUSED` 这类名字，三平台各给一个数，**同一列的四个数字没有一个能通用**。
具体数值与逐条出处见 `data/README.md` §1.1（本文不复述 —— 抄第二份副本的东西迟早和第一份对不上）。

信号从 7 号起就分叉：`SIGBUS` Linux=7 / macOS=10，`SIGSTOP` Linux=19 / macOS=17，
`SIGSTKFLT` Linux 有、macOS **没有**。这些点各有一条断言（`tests/test_catalog_data_m1.py`），
不是靠人复核。

**真跑证据**（`errcode-atlas explain SIGSTKFLT --platform macos`）：

```console
$ py -3.12 -m errcode_atlas explain SIGSTKFLT --platform macos
# 判定：PLATFORM-ABSENT

- 语义：该常量在该平台不存在（正确结果，非失败）
- 查询：SIGSTKFLT · 平台 macos · 域自动探测

## 逐平台
| 平台 | 归因 |
|---|---|
| linux | 16 |

## 平台缺失：macos

## 如何区分

SIGSTKFLT 在 macos 上不存在；在 linux 上存在且取值不同 —— 这是平台缺失，不是编目查不到
```

最后那句"这是平台缺失，不是编目查不到"就是 `PLATFORM-ABSENT` 与 `UNKNOWN` 的分界线：
**前者是"查过，那里没有"，后者是"没查过 / 覆盖不到"**。

### 3.3 无值域：`ERR_*` 没有数字码值

Node 自己抛的 `ERR_*` 异常码只有字符串码名，与 OS errno 也没有映射关系。
硬塞进 `errno` 域会让 `explain 100` 开始编造 —— 于是它是**第四域** `node`，且条目的 `value` 字段**缺省**。

这不是"暂时没填"，是结构性的：`contract.VALUELESS_DOMAINS` 写死这个集合。
报告里这类条目显示"（无数字码值）"而不是 `None` —— **数据缺失与"没有这个字段"必须看起来不一样**。

> 一个由此产生的假歧义差点混进来：`node` 域不挂 `win32-python` 轴，
> 若把"全编目出现过的平台"当分母，**每一次**无平台的名字查询都会判假 `PLATFORM-ABSENT`。
> M3 修的就是这条：分母改成"**命中的域**所覆盖的平台并集"（`plan/03` §2.2 序 8）。

## 四、判定顺序为什么必须写死

"先到先得"的判定会在边界上给出不稳定答案：同一个查询，改动一个分支顺序就换个结论，
而两个结论都"看起来有道理"。所以判定顺序写成表（`plan/03` §2.2 九行 / §3.2 六行），
**每一行对应一条测试**（`tests/test_judgement_order.py`），并且**表的行数也被断言** ——
改表忘改测试会在那里红。

两个顺序上的反直觉决定：

1. **`exit 1` 必须判 `UNATTRIBUTABLE`**。它是"通用失败"，任何具体解释都是猜测。
   把 `1` 解释成"某个具体错误"是本题最贵的那类错 —— 它看起来最有帮助。
2. **`sysexits` 段（64–78）排在 `128+n` 之前**。同一个码可能同时落在两个解释里，
   约定段优先于惯例段。这个顺序如果反了，`64` 会被读成"128+n 之外的特殊值"。

**真跑证据**（`errcode-atlas exitcode 1 --platform linux`）：

```console
$ py -3.12 -m errcode_atlas exitcode 1 --platform linux
# 归因：UNATTRIBUTABLE

- 语义：不可唯一归因（正确结果，非失败）
- 退出码：1 · 平台 linux

## 说明

- 退出码 1 是通用失败，无特定语义；任何具体解释都是猜测
- 不可唯一归因是正确结论，不代表工具失效
```

## 五、基准语料为什么不能由实现自己产出

`bench` 比对的是**结果对象**（`verdict` / 候选 / 逐平台归因 / 退出码），不是渲染文本。
真值来自 `fixtures/*/expected.json`，而它的来源有硬约束（`plan/06` R8）：

> **`expected.json` 必须独立推导，绝不用 `explain` 的输出回填。**

理由很直白：一旦用实现产出真值，改实现 → 重跑 → 真值跟着变 → `bench` 恒绿。
那不再是基准，是实现的自我抄写。M4 的做法是一份**不 import `errcode_atlas`** 的推导脚本
（只读编目 YAML + §5.2 判据），跑完删脚本、不入仓 —— 入库就意味着任何人重跑一次就能让真值跟着变。

规模与覆盖门槛见 `data/README.md` §4（三条门槛各有一条可跑红的判据）。

> **M4 抓到的一处真缺陷**：`expected.json` 里的 `value` 字段**没有任何断言在看** ——
> 名字查询答错号数（`SIGHUP` 答成 2 号）会全绿。改成被 `bench` 断言的 `candidate_values` 之后，
> 又当场验到"改字段名会让 Windows 双视角那条静默退化"，于是判据从"两个视角都有 case"
> 收紧回"两个视角的数值都声明且不相等"。

## 六、两道门，以及"门自己在验东西"

`tools/check_sprint_layout.py`（布局门）与 `tools/check_desensitized.py`（脱敏门）不是脚本，
是**可跑红的断言**。它们的价值不在"现在绿"，在"改错之后会红"。

`tools/verify_gates.py` 逐组制造故障 → 断言门变红 → 还原 → 复绿。
**判据有几条，变异就要覆盖几条**；任一组"改错之后门仍绿"就是假门。

实测中被变异抓出来的三条假门（都是"看起来在管，实际只管了一半"）：

| 假门 | 怎么被抓出来的 |
|---|---|
| `LAYOUT.HANDOFFS` 只遍历已完成里程碑 | 于是"M1 做完没给 M2 留入口"这种情况门照旧全绿 —— 漏掉的正是最该管的那条 |
| `LAYOUT.GAPS` 按"最后一列"取缺口列 | 模板假设缺口在末列，本项目放在首列 → 判据读的是"状态"列，把 `M0` 写进缺口格门仍绿 |
| 脱敏门"整行含 `<` 就放行" | 同一行既写真路径又写占位符时整行放行 → 真泄露漏报 |

三条的共同形态：**判据的靶子与它以为的靶子不是同一个东西**。
判别永远是那一句 —— **"这条判据错过的那一类，我测过吗？"**

## 七、交付形态：为什么是 CLI + Agent Skill 双形态

CLI 是给人用的：一条命令、一份可读的表、一个能进 CI 的退出码。
Agent Skill 是给模型用的：它需要的是**结构化的两路文本 + 一个整数**，而不是解析别人打印的东西。

Skill 侧有一个 Python 级入口 `src/errcode_atlas/api.py::run()`，它只做三件事：
把 argv 交给呈现层、把两路输出收进信封、把出口码原样带出来。**它不做判定** ——
出口码就是 `cli.main` 的返回值，映射仍只在 `contract.exit_code_for_*` 一处
（AST 守门断言 `api.py` 里没有判定态分支）。

为什么不直接 shell 调 CLI：子进程方案要把编码、换行、stderr 分离各处理一遍，
每一处都可能把 `--json` 的字节口径弄歪。同一解释器里收信封，
字节与 CLI 自己的输出**逐字节相同**（`tests/test_api.py` 七条参数化断言）。

Skill 对外声明的契约（五判定态 / 四归因 / 四平台 / 四个出口码）放在 `SKILL.md` 的固定围栏里，
与 `contract.py` 做**集合相等 + 数量相等**的双向断言 ——
放宽成"包含"会漏掉"Skill 里多写了一个已废弃值"，而那正是下游 Agent 会照着执行的声明。

## 九、这份报告刻意没做的事

- **没有复述 `data/README.md` §5 的数值。** 判据、退出码语义、覆盖门槛只在那里定义一次。
  报告里再抄一份，就有了第二份会漂的副本，而 `bench` 与契约测试都只对账第一份。
- **没有手写样例。** 上面每条命令行输出都是从真跑复制的；手写的样例会在某个时刻变成谎言，
  而且没有任何判据会抓到它。
- **没有说"CI 绿"。** 见 §八。
